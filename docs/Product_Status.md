# Product Status

## 当前产品目的

Finance Data Copilot 的当前目的不是做一个普通 AI 聊天工具，而是把金融数据开发中的 SQL 分析、元数据理解、存储过程血缘、人工复核和后续 AI 问答能力沉淀成一个可展示、可扩展、可复用的个人职业发展项目。

当前更准确的产品定位是：

> 面向金融数据开发场景的 AI 数据开发助手，先以元数据资产和存储过程血缘为地基，再逐步扩展到 RAG 问答、指标口径问答、Text-to-SQL 和受控 SQL Agent。

这个项目的核心价值不在于“调用大模型”，而在于先建立可信的数据上下文：哪些表可用、字段是什么意思、主键是什么、哪些过程读写这些表、哪些血缘结果需要人工确认。只有这些基础稳定后，AI 问答和 SQL Agent 才有可靠依据。

## 当前产品主线

当前阶段的产品主线按优先级分为三层。

1. 元数据资产底座

先解决好股库中“哪些表可用、哪些字段可信、字段含义是什么、字段是否主键、是否可为空、是否敏感、属于哪个业务域”等基础问题。元数据是后续血缘分析、RAG 问答、指标问答和 SQL Agent 的共同地基。

2. 血缘分析闭环

在元数据可用的基础上，解析存储过程与表之间的读取、写入、临时表和表间链路关系，并通过血缘复核工作台处理动态 SQL、低置信度边和解析不确定点。

3. AI 辅助能力

在元数据和血缘稳定后，再接入真实大模型能力，包括 SQL 解释增强、数据字典 RAG 问答、指标口径问答、影响分析问答、Text-to-SQL 和受控 SQL Agent。

## 当前最需要先解决的问题

### 问题一：可用表口径

后续所有能力都依赖“可用表”的判断。当前 `metadata_table.is_valid` 已经能区分有效表和下线表，但还需要继续完善以下口径：

- 下线表是否默认从 AI 问答候选中排除
- 业务域为空或“好股库未分类”的表是否需要人工补充分类
- 表重要程度是否需要增加 P0 / P1 / P2 / P3 分级
- 表中文名和业务描述是否足够支撑问答
- 表负责人和更新频率是否可信

当前已提供元数据质量页面，集中展示表是否可用、业务域、字段数、主键完整度、备注完整度和血缘引用次数。下一阶段可以在不覆盖源端分类的前提下，增加“推荐业务分类”或“治理分类”。

当前对 `好股库未分类` 的处理原则是先诊断、后治理，不直接覆盖源端分类。诊断会优先识别仍被血缘引用的未分类表，再识别疑似测试、临时、备份、删除或历史遗留命名的表，然后结合源端 `latest_creat_tm` 识别疑似长期未更新表，最后识别无血缘引用、缺中文名且缺主键的疑似遗留无用表。`metadata_table.updated_at` 表示本地元数据记录更新时间，不等同于公司业务表真实数据更新时间，因此不能单独用于判断表是否报废。

### 问题二：可用字段口径

字段是 SQL 分析、RAG 问答和 Text-to-SQL 的最小知识单元。当前字段中文名、主键、是否为空、字段顺序已经补齐了一部分，但还需要继续完善：

- 字段中文名是否为空
- 字段备注是否为空
- 主键信息是否完整
- 是否为空是否可信
- 字段类型是否标准化
- 固定字段含义是否统一
- 敏感字段是否需要从 `pii_level` 和 `enum_values` 进一步分级
- 枚举值是否需要作为后续问答提示词的一部分

当前已提供字段质量统计，按表统计字段中文名缺失数、备注缺失数、主键缺失、类型异常和是否为空缺失情况。下一阶段可以继续补充敏感等级、枚举值和字段业务价值。

## 短期开发路线

### Step 1：元数据质量收敛

目标：确认哪些表和字段可以作为后续 AI 能力的可信输入。

建议功能：

- 表资产治理视图
- 字段质量检查
- 缺失中文名 / 缺失备注 / 缺失主键统计
- 表重要程度 P0 / P1 / P2 / P3 预留
- 敏感字段分级规则预留

### Step 2：血缘复核体验完善

目标：让 7235 条复核候选可以被有效处理，而不是只作为大列表存在。

建议功能：

- 复核详情抽屉
- 完整 SQL 片段展示
- 相关过程上下文
- 复核优先级
- 低置信度原因分类
- 批量忽略明显噪声

### Step 3：影响分析增强

目标：从“看血缘”升级为“改表前影响评估”。

建议功能：

- 单表上游 / 下游视图
- 读写过程清单
- 关联业务域
- 是否涉及下线表
- 是否涉及高优先级表
- 是否存在需复核血缘

### Step 4：AI 问答接入

目标：在元数据和血缘稳定后，把 AI 接入到可信知识底座上。

建议功能：

- 数据字典 RAG 问答
- 指标口径问答
- 表影响范围问答
- SQL 解释增强
- 受控 Text-to-SQL 原型

## 当前不做事项

当前阶段继续不做以下内容：

- 登录系统
- 多租户
- 复杂权限系统
- 真实业务明细数据读取
- 公司业务库写操作
- 执行公司存储过程
- 执行用户输入 SQL
- 直接上线 Text-to-SQL
- 复杂 SQL Agent

## 当前安全边界

- 公司 SQL Server 只作为只读元数据来源。
- 好股库通过链接服务器读取系统目录和存储过程定义。
- 不读取真实业务明细数据。
- 不执行公司 SQL。
- 不执行存储过程。
- 复核结果只写入本地 PostgreSQL。
- Cookie、账号、密码、内网连接信息不得写入代码或文档。

## 下一步建议

下一步建议优先做“元数据质量收敛”，而不是继续扩展 AI 功能。

最小可行下一步：

1. 梳理“好股库未分类”中的高价值表，优先处理仍被血缘引用的未分类表。
2. 设计推荐业务分类口径，保留源端业务域，不直接覆盖 `metadata_table.business_domain`。
3. 补充表重要程度 P0 / P1 / P2 / P3 规则。
4. 补充敏感字段分级、枚举值和字段业务价值规则。
5. 在元数据质量稳定后，再继续做血缘复核详情和 RAG。
